================================================================================
DWH — послойное описание (ODS → DDS → DM)
================================================================================

О чём предметная область
-------------------------------------------

Представь автопарк / парк техники и людей, которые им распоряжаются.

• Диспетчер — человек (имя, телефон, дневная или ночная смена).
• Техника — машина или единица оборудования (номер, тип, статус:
  в работе / в ремонте / простаивает).
• Запись о работе техники (в базе таблица equipment_assignments) —
  это факт: «такой-то диспетчер в такой промежуток времени работал
  на такой-то технике, отработано N часов».

  В отчётах это часто называют «назначение» — имеется в виду именно
  ЭТА запись о работе (кто + какая машина + когда + сколько часов),
  а НЕ «дневная/ночная смена» диспетчера.
  Смена day/night — это отдельное поле shift_code у диспетчера.


Общий поток
-----------

  PostgreSQL (источник, здесь не разбираем)
        ↓  копируем почти как есть
      ODS   — сырой склад в ClickHouse
        ↓  чистим дубли, храним историю изменений справочников
      DDS   — история версий людей/техники + факты работы
        ↓  считаем готовые дневные таблицы под отчёты
       DM   — три витрины для аналитики


================================================================================
СЛОЙ ODS (Operational Data Store)
================================================================================

Зачем: положить данные из источника в ClickHouse «как есть», чтобы
дальше не ходить в PostgreSQL. Плюс одна служебная колонка — когда
строка попала в ODS.

Как попадают данные:
  • таблица пустая → заливаем всё из источника;
  • таблица уже не пустая → только новые строки или более свежие
    (по updated_at / по изменившимся полям).
TRUNCATE не используем.

Движок ReplacingMergeTree: со временем сам может схлопнуть дубли
по одному id, но КОГДА — неизвестно. Поэтому дальше в DDS мы сами
явно берём «последнюю версию» через argMax, не ждём merge.


1) ods.dispatchers — диспетчеры
-------------------------------
id           — номер диспетчера (как в источнике)
first_name   — имя
last_name    — фамилия
phone        — телефон (может быть пусто)
shift_code   — тип его смены: day или night
is_active    — работает ли сейчас (1/0; в источнике было true/false)
updated_at   — когда запись меняли в источнике
_loaded_at   — когда строка попала в ODS (добавляем мы)


2) ods.equipment — техника
--------------------------
id                — номер единицы техники
inventory_number  — инвентарный номер
name              — название
equipment_type    — тип (например экскаватор, самосвал и т.п.)
status            — in_service (в строю) / repair (ремонт) / idle (простой)
dispatcher_id     — за кем сейчас закреплена (может быть пусто)
updated_at        — когда меняли в источнике
_loaded_at        — когда попало в ODS


3) ods.equipment_assignments — записи о работе техники
------------------------------------------------------
id             — номер такой записи
equipment_id   — какая техника
dispatcher_id  — какой диспетчер
started_at     — начало работы
ended_at       — конец работы (может быть пусто, если ещё идёт)
work_hours     — сколько часов отработали
created_at     — когда запись создали в источнике
_loaded_at     — когда попало в ODS

Что меняем при загрузке в ODS (по сравнению с PostgreSQL):
  • почти ничего по смыслу — те же поля;
  • bool → 0/1;
  • время приводим к DateTime Europe/Moscow;
  • добавляем только _loaded_at.
Почему так: ODS — «фото источника», без бизнес-логики.


================================================================================
СЛОЙ DDS (Detail Data Store)
================================================================================

Зачем: хранить ИСТОРИЮ изменений справочников и факты работы с привязкой
к той версии человека/техники, которая была актуальна в момент работы.

Перед загрузкой из ODS всегда делаем дедуп:
  одна актуальная строка на id = GROUP BY id + argMax(..., updated_at).
Почему: в ODS могут лежать две версии одной строки, пока ClickHouse
не сделал merge.


A) dds.dim_dispatcher — диспетчер С ИСТОРИЕЙ (SCD Type 2)
---------------------------------------------------------

Идея: если у Даши сменили телефон, старая строка НЕ затирается.
Закрываем старую версию и добавляем новую. Тогда отчёт «за август»
видит августовский телефон, а не сегодняшний.

dispatcher_sk   — технический ключ ВЕРСИИ (каждая новая версия = новый sk)
dispatcher_id   — бизнес-номер человека (тот же id, что в ODS)
first_name      — имя
last_name       — фамилия
phone           — телефон в ЭТОЙ версии
shift_code      — day/night в ЭТОЙ версии
is_active       — активен ли в ЭТОЙ версии
valid_from      — с какого момента версия действует
valid_to        — до какого момента (у текущей — «открытое» далеко в будущем)
is_current      — 1 = сейчас актуальная версия, 0 = уже закрыта

Как меняются данные ODS → эта таблица:
  • Новый человек (id ещё не было) → одна строка:
      valid_from = updated_at из ODS, valid_to = «открыто», is_current = 1,
      новый dispatcher_sk.
  • Человек есть, поля НЕ изменились → ничего не делаем.
  • Человек есть, поля изменились (телефон, смена, ФИО, is_active):
      1) берём ВСЕ старые версии этого id из DDS;
      2) закрытые (is_current=0) копируем как были;
      3) бывшую текущую закрываем: valid_to = updated_at из ODS, is_current=0;
      4) добавляем новую версию с новыми полями и НОВЫМ sk;
      5) удаляем из таблицы строки этого id и вставляем собранный набор.
Почему delete+insert набора, а не UPDATE всей таблицы: в ClickHouse
точечный UPDATE = тяжёлая мутация; так принято для SCD2.


B) dds.dim_equipment — техника С ИСТОРИЕЙ (SCD Type 2)
------------------------------------------------------

Тот же принцип, что у диспетчеров.

equipment_sk      — ключ версии строки техники
equipment_id      — бизнес-номер техники
inventory_number  — инвентарный номер
name              — название
equipment_type    — тип
status            — статус в ЭТОЙ версии (in_service / repair / idle)
dispatcher_id     — за кем была закреплена в этой версии
valid_from / valid_to / is_current — как у диспетчера

Меняется аналогично: смена status или других полей → закрыли старую
версию, открыли новую.


C) dds.fct_assignment — факты работы техники
--------------------------------------------

Сюда попадают строки из ods.equipment_assignments.
Только НОВЫЕ id: уже загруженные повторно не вставляем (append-only).

assignment_id   — номер записи о работе (= id из ODS)
equipment_sk    — КАКАЯ ВЕРСИЯ техники была на момент started_at
dispatcher_sk   — КАКАЯ ВЕРСИЯ диспетчера была на момент started_at
equipment_id    — номер техники (дубль для удобства)
dispatcher_id   — номер диспетчера (дубль для удобства)
started_at      — начало работы
ended_at        — конец работы
work_hours      — часы
equipment_type  — тип техники НА МОМЕНТ работы (скопировали из версии dim)
shift_code      — смена диспетчера НА МОМЕНТ работы (скопировали из версии dim)

Как выбираем sk:
  ASOF JOIN: берём версию dim, у которой started_at попадает в
  [valid_from, valid_to).
Почему sk, а не только id: если джойнить по id к «текущей» версии,
прошлые работы «увидят» сегодняшний телефон/статус — отчёт за прошлый
месяц будет неверным.
Почему сразу кладём equipment_type и shift_code в факт: чтобы простые
срезы не требовали JOIN к справочникам.


================================================================================
СЛОЙ DM (Data Mart) — три готовые таблицы для отчётов
================================================================================

Зачем: аналитик делает SELECT * / GROUP BY — без сложных JOIN.
Пересчёт каждый прогон DAG целиком: считаем во временную таблицу,
потом EXCHANGE (атомарно подменяем снимок). Без TRUNCATE.
Данные берутся из DDS.


1) dm.equipment_utilization_daily
   «Что делала каждая машина за день — сколько отработала»
------------------------------------------------------------

Одна строка = один календарный день + одна единица техники.
Считается только из фактов работы (fct_assignment) + справочники для имён/типа.
Строка есть, только если в этот день были записи о работе.

work_date               — день (дата начала работы из факта)
equipment_id            — какая техника
inventory_number        — инвентарный номер
equipment_name          — название
equipment_type          — тип
dispatcher_id           — диспетчер (если за день их несколько — берётся один)
dispatcher_first_name   — имя
dispatcher_last_name    — фамилия
shift_code              — day/night диспетчера
assignments_cnt         — сколько записей о работе было у этой машины за день
work_hours_sum          — сумма часов по этим записям

Как читать:
  • много work_hours_sum → машина много работала (топ загрузки);
  • строки нет за день → в этот день по фактам работ не было;
  • простой/ремонт по статусу смотри во витрине 3 (здесь статуса нет — чтобы не путать).


2) dm.dispatcher_workload_daily
   «Какая нагрузка на каждого диспетчера за день»
-------------------------------------------------

Одна строка = один день + один диспетчер.

work_date               — день
dispatcher_id           — кто
dispatcher_first_name   — имя
dispatcher_last_name    — фамилия
shift_code              — day/night
assignments_cnt         — сколько записей о работе он вёл за день
equipment_cnt           — на скольких РАЗНЫХ машинах работал за день
work_hours_sum          — сумма часов

Как читать:
  • высокий assignments_cnt и work_hours_sum → человек перегружен;
  • низкие — недозагружен;
  • assignments_cnt — это число записей о работе, НЕ число «смен day/night».


3) dm.equipment_nonproductive_daily
   «Сколько часов конкретная машина не работала и почему»
----------------------------------------------------------

Одна строка = один день + одна единица техники.
Только дни, когда машина была в простое и/или ремонте (хотя бы частично).

work_date             — день
equipment_id          — какая машина
inventory_number      — инвентарный номер
equipment_name        — название
equipment_type        — тип
hours_idle            — часов в статусе idle (простой / не нагрузили)
hours_repair          — часов в статусе repair (ремонт / сломана)
hours_not_in_service  — всего часов «не в работе» = idle + repair
work_hours_fact       — сколько часов реально отработала по фактам в этот день
                        (обычно 0, если весь день в idle/repair)

Как читать:
  • сортировка по hours_not_in_service DESC за вчера → кто больше всех стоял;
  • смотри hours_idle vs hours_repair → почему (не нагрузили vs сломана);
  • пример: 10 ч idle + 14 ч repair → 24 ч не в работе, причины разные в течение дня.

Считается из dds.dim_equipment (SCD2, пересечение версии с сутками в часах)
и dds.fct_assignment (контроль фактических часов).


Как три витрины дополняют друг друга
------------------------------------
• Кто сколько отработал часов / сколько было работ — витрины 1 и 2.
• Какая машина сколько часов стояла и почему (idle/repair) — витрина 3.
• Перегруз соседней техники при простое другой — витрина 1 (часы работы)
  рядом с витриной 3 (часы простоя).
• Топ за месяц — GROUP BY + ORDER BY по витринам 1–3,
  отдельные таблицы для топов не делаем.


================================================================================
Кратко: что меняется при переходе слоя
================================================================================

ODS → DDS (справочники):
  добавляем историю (valid_from/valid_to/is_current) и sk версии;
  при изменении полей не затираем прошлое, а закрываем старую версию.

ODS → DDS (записи о работе):
  только новые id; подставляем sk версии на дату начала работы;
  копируем тип техники и смену диспетчера «на тот момент».

DDS → DM:
  агрегируем по дням в три готовые таблицы под три вопроса бизнеса;
  все нужные имена/типы/статусы уже в строке витрины.

Рядом (не слой аналитики): MinIO (S3) — cold volume ClickHouse.
Растущие таблицы партиционированы по месяцу; данные старше 15 месяцев
через TTL TO VOLUME на S3, более свежие — на локальном hot.
SELECT как обычно. Справочники/dims остаются локально.

BI: Apache Superset читает только DM (см. docs/SUPERSET.md).
